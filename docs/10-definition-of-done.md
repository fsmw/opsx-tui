# Definition of Done — OPSX TUI

## 1. Purpose

This document defines when an **OPSX TUI** change can be considered done.

Its goal is to prevent an implementation from being considered finished solely because:

- the code compiles;
- the interface opens;
- the agent claims it finished;
- the tasks were checked off;
- a manual test worked;
- the process finished with exit code 0.

The Definition of Done, hereinafter **DoD**, establishes the minimum mandatory criteria to:

- complete a task;
- complete a change;
- run `/opsx:verify`;
- archive;
- publish a version;
- accept work generated by an agent.

This document is normative for:

- OpenSpec tasks;
- reviews;
- implementation;
- testing;
- documentation;
- security;
- CI;
- releases;
- agents.

---

# 2. Core principle

A change is done when sufficient evidence exists that:

```text
it meets the requirements,
respects the architecture,
passes the tests,
does not introduce critical risks,
is documented,
can be verified,
and can be archived.
```

The agent's claim does not constitute sufficient evidence.

---

# 3. Done levels

OPSX TUI shall use four levels.

## 3.1 Task Done

An individual task is implemented and verified.

## 3.2 Change Done

All tasks and requirements of the change are complete.

## 3.3 Release Ready

The set of changes is ready for publication.

## 3.4 Archived

The change was verified and correctly archived in OpenSpec.

---

# 4. Task Done

A task may be marked as completed when:

- its objective is implemented;
- no placeholders remain;
- the expected behavior can be demonstrated;
- tests exist where applicable;
- it does not break contracts;
- it does not leave unrecorded debt;
- its code is integrated;
- it does not depend on hidden manual steps.

## 4.1 Not considered Task Done

- file created but empty;
- function with `pass`;
- pending TODO;
- skipped test;
- known error not recorded;
- mock used in production;
- partial implementation;
- behavior only demonstrated manually;
- dead code;
- undocumented configuration.

---

# 5. Change Done

A change is Done when it meets all applicable criteria from the following categories:

```text
Requirements
Implementation
Architecture
Testing
Quality
Security
Documentation
Operation
Verification
OpenSpec
```

---

# 6. Functional requirements

## 6.1 Mandatory

- All change requirements are implemented.
- All scenarios can be demonstrated.
- There is no out-of-scope behavior.
- Relevant edge cases are covered.
- Expected errors are understandable.
- Available actions respect capabilities.
- States are explainable.
- Rules are not duplicated.

## 6.2 Evidence

- tests;
- functional validation;
- screenshots or logs where applicable;
- artifact review;
- `/opsx:verify` result.

## 6.3 Criterion

There must be no partially implemented requirement without explicit indication.

---

# 7. Implementation

## 7.1 Mandatory

- The code is complete.
- There are no placeholder functions.
- There are no unnecessary generic exceptions.
- Errors are normalized.
- Models are consistent.
- Paths are validated.
- Concurrency is handled.
- Cancellation is safe where applicable.
- Resources are released.
- Child processes are controlled.

## 7.2 Rules

- Do not use `shell=True`.
- Do not access the filesystem from UI.
- Do not run subprocesses from widgets.
- Do not persist secrets.
- Do not duplicate OpenSpec canonical data.
- Do not compute lifecycle in presentation.
- Do not couple UI to a specific backend.

---

# 8. Architecture

## 8.1 Mandatory

- Respects layers:
  - domain;
  - application;
  - infrastructure;
  - presentation.
- Dependencies point in the correct direction.
- Adapters implement ports.
- Domain models do not import Textual.
- UI consumes services.
- Rules are in services or domain.
- Relevant decisions respect ADR.

## 8.2 ADR

If the change:

- introduces a major dependency;
- changes persistence;
- changes architecture;
- changes security;
- changes compatibility;
- replaces a decision;

it must include an ADR.

---

# 9. Testing

## 9.1 Mandatory

- Unit tests.
- Contract tests where applicable.
- Integration tests where applicable.
- TUI tests where applicable.
- Security tests where applicable.
- Regression test for bugs.

## 9.2 Rules

- Do not depend on real services.
- Do not use real home directory.
- Do not write outside temp.
- Do not require credentials.
- Do not use long sleeps.
- Do not hide flakes.
- Python 3.11 must pass.

## 9.3 Coverage

Minimum targets:

```text
Total: 80 %
Critical domain: 95 %
Security: 90 %
Critical adapters: 85 %
```

A decrease requires justification.

---

# 10. Static quality

## 10.1 Mandatory

```text
Ruff
MyPy
Pytest
```

## 10.2 Ruff

- no errors;
- no broad ignores;
- no rules disabled without reason.

## 10.3 MyPy

- no critical errors;
- no accidental `Any` in contracts;
- public types defined.

## 10.4 Format

The project must maintain consistent formatting.

---

# 11. Compatibility

## 11.1 Python

Must work on:

```text
3.11
3.12
3.13
3.14
```

Mandatory gate:

```text
Python 3.11
```

## 11.2 Platform

Linux is mandatory.

macOS and Windows per declared scope.

## 11.3 OpenSpec

- version detected;
- capabilities evaluated;
- degraded mode available;
- incompatibility visible.

---

# 12. Security

## 12.1 Mandatory

- Do not use shell.
- Validate paths.
- Detect external symlinks.
- Redact secrets.
- Filter environment.
- Confirm modifying operations.
- Show real sandbox.
- Respect network policy.
- Inspect Git when applicable.
- Prevent incompatible concurrency.
- Record changes.
- Validate functional result.

## 12.2 Findings

Cannot be archived with:

- critical vulnerability;
- exposed secret;
- uncontrolled external write;
- command injection;
- path traversal;
- unresolved Git conflict;
- failed security test.

---

# 13. Documentation

## 13.1 Mandatory

Update when applicable:

- README;
- architecture docs;
- functional contract;
- domain model;
- OpenSpec contract;
- lifecycle;
- backend;
- security;
- testing;
- ADR;
- user help.

## 13.2 Public code

Must have docstrings when intent is not obvious.

## 13.3 Configuration

Every new option must document:

- name;
- type;
- default;
- scope;
- precedence;
- security;
- example.

---

# 14. UX and TUI

## 14.1 Mandatory

- Keyboard navigation.
- Visible focus.
- Understandable error.
- Empty state.
- Loading state.
- Narrow terminal.
- Visible cancellation.
- Documented shortcuts.
- Confirmation for risk.

## 14.2 Not acceptable

- modal with no exit;
- action with no feedback;
- process that blocks UI;
- error only in log;
- silent state;
- destructive key without confirmation.

---

# 15. Observability

## 15.1 Mandatory

- start;
- end;
- duration;
- executor;
- backend;
- model;
- exit code;
- affected files;
- errors;
- functional result;
- cancellation;
- timeout.

## 15.2 Logs

- redacted;
- bounded;
- queryable;
- exportable;
- no secrets.

---

# 16. Persistence

## 16.1 Mandatory

- versioned schema;
- migrations when applicable;
- transactions;
- recovery;
- do not duplicate OpenSpec;
- retention;
- appropriate permissions.

## 16.2 SQLite

When a change modifies persistence:

- migration test;
- rollback test;
- compatibility test;
- interrupted state test.

---

# 17. OpenSpec

## 17.1 Mandatory artifacts

The change must have:

- proposal;
- design when applicable;
- delta specs;
- tasks;
- verification.

## 17.2 Tasks

- all checked off;
- reflect real implementation;
- do not auto-check without evidence;
- do not delete pending tasks to close.

## 17.3 Specs

- updated;
- consistent scenarios;
- no contradictions;
- no orphan requirements.

## 17.4 Archive

Do not archive until:

- verify is satisfactory;
- no blockers exist;
- fingerprint is current;
- artifacts are valid;
- CI passes.

---

# 18. Verification

## 18.1 `/opsx:verify`

Must evaluate:

- requirements;
- tasks;
- tests;
- architecture;
- security;
- documentation;
- artifacts;
- Git;
- regressions.

## 18.2 Acceptable result

```text
passed
passed-with-warnings
```

`passed-with-warnings` only allows archive if:

- there are no blocking warnings;
- they are documented;
- there is explicit acceptance.

## 18.3 Unacceptable result

```text
failed
interrupted
stale
unknown
```

---

# 19. Closure blockers

A change is not Done if there is:

- incomplete requirement;
- failed test;
- skipped test without reason;
- MyPy error;
- Ruff error;
- Python 3.11 failure;
- exposed secret;
- unsafe path;
- Git conflict;
- missing migration;
- missing doc;
- missing ADR;
- inconsistent lifecycle;
- stale verify;
- critical TODO;
- unobservable behavior;
- unjustified dependency.

---

# 20. Technical debt

## 20.1 Allowed

Only if:

- does not block requirements;
- does not affect security;
- is recorded;
- has priority;
- has an owner or future change;
- does not hide partial implementation.

## 20.2 Not allowed

- unsafe workaround;
- disabled test;
- temporary hardcode;
- secret in code;
- rule duplication;
- architecture bypass.

---

# 23. Definition of Ready for archive

A change is ready for archive when:

- state is `ready-to-archive`;
- verify is current;
- all tasks are complete;
- CI is green;
- Git is reviewed;
- docs are updated;
- there are no blockers;
- there are no critical findings;
- the user accepts archive.

---

# 24. Release Ready

A version is ready when:

- all included changes are archived;
- changelog is updated;
- version is defined;
- package build is successful;
- wheel is tested;
- sdist is tested;
- clean install;
- `opsx-tui --version`;
- smoke test;
- documentation is published;
- dependencies are audited;
- release notes.

---

# 25. Exceptions

## 25.1 Allowed

Only with:

- justification;
- scope;
- risk;
- responsible party;
- date;
- approval;
- follow-up.

## 25.2 Not allowed

No exceptions are allowed for:

- secrets;
- shell execution;
- path traversal;
- critical tests;
- Python 3.11;
- critical vulnerabilities;
- archive without verify.

# 28. Agent responsibility

The agent must:

- review DoD before implementing;
- create tests;
- update docs;
- report limitations;
- not mark tasks without evidence;
- run gates;
- report failures;
- not auto-archive if criteria are missing.

---


```text
ready-to-archive
```


```text

```

---

# 30. Invariants

1. Done requires evidence.
2. Complete tasks are not enough.
3. Exit code 0 is not enough.
4. Stale verify does not allow archive.
5. Red CI blocks.
6. Critical security blocks.
7. Python 3.11 blocks if it fails.
8. Missing docs may block.
9. Missing ADR may block.
10. Scope creep is not accepted.
11. Every bug requires regression.
12. Every adapter requires contract tests.
13. All relevant UI requires TUI tests.
14. Every persistence change requires migration.
15. Every archive requires confirmation.

---

# 31. Constraints for the implementing agent

The agent shall not:

- declare Done by perception;
- mark tasks just to close;
- skip tests;
- disable gates;
- reduce coverage without explanation;
- hide warnings;
- archive with stale verify;
- ignore Python 3.11;
- leave critical TODOs;
- introduce silent debt;
- omit ADR;
- omit documentation;
- assume functional success;
- skip security;
- declare release ready without packaging tests.

---

# 32. Summary

The DoD answers:

```text
Does it work?
Does it comply?
Is it tested?
Is it secure?
Does it respect architecture?
Is it documented?
Can it be verified?
Can it be maintained?
```

The main rule is:

```text
Done does not mean the agent stopped working.
It means the change can be sustained with evidence.
```
